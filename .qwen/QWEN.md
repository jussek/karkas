# Каркасон онлайн — инструкции для Qwen Code

## Роль Qwen

Qwen Code является исполнителем.

Архитектурные решения, правила игры, структуру игрового движка, модель данных и критерии готовности определяет внешний архитектор.

Qwen не должен самостоятельно:

* менять архитектуру;
* добавлять игровые правила;
* переименовывать публичные типы без задания;
* делать крупный рефакторинг;
* удалять существующую функциональность;
* переходить к следующему этапу;
* изменять Supabase production schema без явного задания.

## Правило выполнения

Каждая задача выполняется буквально по указанному заданию.

Если в задании указаны конкретные файлы, сначала работать только с ними.

Если во время работы обнаружена проблема вне области задачи:

1. не исправлять её автоматически;
2. сообщить о ней в финальном отчёте;
3. продолжить только если она не блокирует текущую задачу;
4. если проблема блокирует задачу — остановиться и сообщить об этом.

## Проверки

После изменений выполнять только проверки, указанные в задании.

Если задание требует тесты:

* запускать тесты;
* сообщать точный результат.

Если задание требует TypeScript:

* запускать указанный TypeScript check;
* сообщать точный результат.

Если задание требует build:

* запускать build;
* сообщать точный результат.

Не считать задачу выполненной только потому, что код выглядит корректно.

## Git

Не делать commit и push, если это явно не указано в задании.

Перед commit:

* показать изменённые файлы;
* выполнить требуемые проверки.

Не делать force push.

Не переписывать историю без явного задания.

## Supabase

Supabase является отдельным persistence/backend слоем проекта.

Не изменять production database напрямую.

Не выполнять:

* DROP;
* TRUNCATE;
* массовый DELETE;
* destructive ALTER;
* удаление таблиц;
* удаление данных.

SQL migrations создавать только по отдельному заданию.

Игровые правила не должны зависеть от прямых SQL-запросов.

## Game Engine

Игровой движок должен оставаться максимально детерминированным и тестируемым независимо от Supabase и UI.

Не переносить игровые правила в React-компоненты.

Не смешивать:

* UI;
* persistence;
* game rules;
* tile catalog.

без отдельного архитектурного задания.

## Tile Catalog

Каталог карт является отдельным источником данных.

Не менять классификацию существующих карт без конкретного задания.

Не заменять изображения карт и не переименовывать asset-файлы без конкретного задания.

## Отчёт

После выполнения задачи сообщить:

1. Что изменено.
2. Какие файлы изменены.
3. Какие проверки выполнены.
4. Результат каждой проверки.
5. Git SHA, если был commit.
6. Push SHA, если был push.
7. Что обнаружено, но НЕ изменено.

Не писать длинный анализ архитектуры.
Не придумывать результаты проверок.
Не заявлять об изменениях, которых нет в Git.
